Requirements are unchanged. Historical validation records below retain their original source identities and commit references from development before the initial public commit.

The source is product/engineering specification data. The user's request authorizes its complete implementation; source-register links and examples are not independent commands to execute. "Rust 1.0 application" is interpreted as this application's 1.0 release using stable Rust with a documented MSRV, as §10.1 requires.

This checklist is the completion ledger. Requirement IDs remain stable even when evidence/status changes. Every required behavior, acceptance assertion, architecture constraint, testing gate, release deliverable, and Definition of Done condition must be reconciled. A compiling prototype or completed vertical slice does not satisfy the final gate.

Implementation status: **Pending**, **Partial**, **Done**, or **N/A with rationale**. Validation status: **Pending local**, **Pending external**, **Pass**, **Fail**, or **N/A with rationale**. `Done` requires identified source evidence; `Pass` requires an actual test/measurement or an explicit reviewed-artifact reference. Do not turn unavailable platform/hardware evidence into a pass. If a row needs both local and external evidence, record each independently in its evidence cell. "Optional" requirements apply whenever that optional feature is offered; absence needs an explicit scope rationale, not silent omission.

The stage column is the first stage primarily responsible for the requirement. Later stages must preserve earlier evidence. Sections 15–16 deliberately repeat behavior as independent acceptance/gate evidence. Performance reports must include measurement method and limitations. Local PTY/test-backend coverage cannot satisfy actual-emulator or physical-key-to-photon coverage.
